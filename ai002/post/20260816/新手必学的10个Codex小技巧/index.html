新手必学的10个Codex小技巧

2026年8月16日
| 阅读

PART.0****1

为什么你和Codex聊了半天，它还是没帮你完成任务？

很多人安装好Codex后，输入的第一句话往往是：“帮我写一个程序。”

几分钟后，Codex的确生成了不少代码，但真正运行时却发现：功能不是自己想要的、原有文件被改乱了、依赖装了一大堆，甚至连项目怎么启动都不清楚。

问题通常不在于Codex不够聪明，而在于我们仍然把它当成一个“回答问题的聊天机器人”。

Codex更像是一名可以进入项目、读取文件、修改代码、运行命令和检查结果的开发协作者。要让它真正帮你干活，关键不是不断追问，而是学会给它明确的任务、工作范围和验收标准。

先给结论

高质量使用Codex的核心不是寻找一句“神奇提示词”，而是建立完整工作闭环：给出目标、提供上下文、设置边界、分步执行、验证结果、审查改动。

高质量Codex任务的四个基本要素

下面这10个技巧，尤其适合刚开始使用Codex的新手。文中的命令示例以Codex CLI为主，其中的任务设计方法同样适用于桌面端和IDE扩展。

技巧 1｜不要只说“做什么”，还要说明“做到什么程度”

“帮我优化代码”、“帮我做一个网站”这类指令看似明确，实际上给Codex留下了大量需要自行猜测的空间。一个更有效的任务说明，至少应包含目标、上下文、约束和完成标准。

推荐写法

目标：修复用户连续登录失败后仍可继续尝试的问题。
上下文：登录逻辑位于 src/auth，现有测试位于 tests/auth。
约束：不要修改数据库表结构，不新增第三方依赖。
完成标准：连续输错5次密码后锁定账号30分钟，现有测试和新增测试全部通过。

任务越接近一份清晰的工作任务单，Codex的执行结果通常越可靠。与其在生成结果后不断纠正方向，不如在开始前先把目标和验收标准说清楚。

无效对话与有效任务的差别

技巧 2｜一定要在正确的项目目录中启动Codex

Codex会把启动时所在的目录视为当前工作目录。如果在错误目录中启动，它可能无法找到项目文件，也可能把新文件创建在不合适的位置。

启动前检查

进入Codex后，可以使用/status检查当前项目根目录、可写范围、权限策略和会话状态。第一次练习建议优先使用空目录、测试项目或单独分支，不要直接修改生产环境。

技巧 3｜先让Codex阅读项目，再让它修改文件

面对一个已有项目，不要一上来就让Codex写代码。更好的方式是先让它了解项目结构、启动方法、依赖关系和现有约定。

先理解、后修改

先不要修改任何文件。请阅读 README.md、项目依赖文件和 src 目录，并说明：
1. 这个项目的主要功能；
2. 项目如何启动；
3. 核心目录分别负责什么；
4. 如果要修改登录功能，可能涉及哪些文件；
5. 当前还缺少哪些必要信息。

这样做可以提前检查Codex是否正确理解项目，也能在动手之前发现信息缺失、方向错误或潜在风险。对于不熟悉的代码仓库，“先理解、后修改”通常比直接生成代码更省时间。

技巧 4｜复杂任务先规划，不要立即执行

如果任务涉及多个文件、数据库、接口或前端页面，建议先让Codex制定方案。在Codex CLI中可以使用/plan，也可以直接要求它先输出计划、暂时不要修改文件。

复杂任务先规划

/plan这是一个多步骤任务。请先分析现有代码并给出实施计划，暂时不要修改文件。
计划中需要列出：涉及文件、修改目的、潜在风险和验证方法。
等我确认方案后再开始执行。

规划的价值不是让回复看起来更专业，而是在真正修改代码前，帮助你判断Codex是否理解需求、修改范围是否过大、是否准备引入不必要的依赖，以及有没有更简单的实现方式。

Codex任务从理解到验收的完整闭环浓

技巧 5｜明确告诉Codex“哪些事情不能做”

很多返工不是因为功能没有实现，而是Codex顺手做了你并不希望它做的事情。因此，任务中最好加入少量但关键的限制条件。

• 不要删除现有文件，也不要大范围重构无关代码。

• 不要修改数据库表结构、既有接口参数和部署配置。

• 不要升级框架版本；新增生产依赖前必须说明原因并等待确认。

• 不要把账号、密码、API Key或生产密钥写入代码和提示词。

权限提示

新手建议先保留默认审批和沙箱设置。看到命令后先判断它准备做什么，再决定是否允许执行；不要因为嫌确认麻烦，就一开始把全部权限交给工具。

技巧 6｜把大任务拆成可以检查的小任务

“从零开发一个完整管理系统”并不是一个适合一次性交给Codex的任务。更合理的方式是拆成项目结构、登录接口、自动化测试、前端页面、联调、异常处理和部署说明等阶段。

限制本轮任务范围

本轮只完成登录接口，不开发前端页面。完成后请停止，并说明：
1. 修改了哪些文件；
2. 接口如何调用；
3. 运行了哪些测试；
4. 下一步建议做什么。

拆分任务并不会降低效率。相反，它能减少错误累积，让每一次修改都处于可检查、可回退的状态。

技巧 7｜把“如何验证”直接写进任务

只要求Codex“完成代码”，往往只能得到“看起来已经完成”的结果。更可靠的方式，是提前告诉它用什么命令证明任务已经完成。

把验证写进完成标准

完成修改后，请依次执行：
1. npm test
2. npm run lint
3. npm run build如果出现错误，请先分析原因并修复。
只有以上命令全部通过，并确认原有功能未受影响后，才算任务完成。

不同项目的验证方式可能是单元测试、接口测试、编译构建、代码格式检查、类型检查、页面截图或实际运行结果。Codex不应该只负责生成代码，还应该帮助你测试、检查和复核。

技巧 8｜修改前保存状态，修改后检查差异

让Codex修改已有项目之前，最好先使用Git保存当前状态。这样即使结果不符合预期，也可以清楚比较变化并安全回退。

修改前保存，修改后审查

git status
git add .
git commit -m “保存Codex修改前的项目状态”/diff
/review

/diff用于查看当前项目的代码差异，/review可以从代码审查角度检查逻辑错误、遗漏的异常处理、潜在回归、缺少的测试和安全风险。AI生成的代码也需要审查，能够生成代码不等于代码已经正确，更不等于可以直接上线。

技巧 9｜一个会话只处理一个相对完整的目标

不要在同一个会话中先修改登录功能，接着写宣传文案，然后分析Excel，最后又回来处理登录报错。随着上下文不断变长，Codex更容易混淆旧要求和新要求。

如果原任务仍在继续，就保留当前会话；如果已经切换到新的独立目标，可以使用/new开始新会话。当会话很长但仍需继续当前任务时，可以使用/compact压缩较早内容，保留关键背景和决策。

上下文管理原则

一个会话围绕一个相对完整的工作目标展开。合理管理上下文，比不断补充“你还记得前面说过什么吗”更有效。

技巧 10｜把重复要求写进AGENTS.md

如果每次都要提醒Codex修改后运行哪些测试、不允许新增哪些依赖、项目使用什么代码规范、哪些目录不能修改，说明这些内容已经不是临时要求，而是项目长期规则。

AGENTS.md 落地示例

这时可以在项目根目录创建AGENTS.md。Codex会在开始工作前读取其中的项目说明。在Codex CLI中，可以先使用/init生成基础版本，再根据项目的真实运行方式进行修改。

AGENTS.MD 示例

# 项目协作要求## 项目运行
- 使用 npm test 运行测试
- 使用 npm run lint 检查代码格式## 修改限制
- 不修改数据库表结构
- 不删除已有接口
- 新增生产依赖前先说明原因## 完成标准
- 相关测试全部通过
- 列出修改文件、验证结果和潜在风险

AGENTS.md不需要写得很长。短小、准确、能够真正指导项目工作的规则，通常比一份堆满空泛要求的长文档更有价值。

一份可以直接复制的Codex任务模板

如果暂时不知道如何组织任务，可以直接套用下面的模板。删除不适用的内容，再替换成当前项目的真实信息即可。

CODEX通用任务模板

【任务目标】
请完成：【相关上下文】
重点查看以下文件、目录或错误信息：【允许修改的范围】
可以修改：【限制条件】
不要修改：
新增依赖、删除文件或执行高风险命令前，需要先征得我的确认。【执行方式】
先阅读相关文件并说明你的理解。
如果任务较复杂，先给出实施计划，确认后再修改。【完成标准】
1. 功能达到预期；
2. 相关测试、检查和构建命令全部通过；
3. 不影响已有功能；
4. 最后列出修改文件、验证结果、潜在风险和后续建议。

写在最后

真正高效地使用Codex，不是学会多少“神奇提示词”，而是建立一套清晰的协作流程：给出目标，提供上下文，设置边界，分步执行，验证结果，审查改动。

从聊天工具到项目协作者

当你只把Codex当成聊天工具时，它只能不断给你建议；当你开始给它工作目录、项目规则、验收标准和检查方法时，它才真正变成能够参与实际工作的开发协作者。

对于刚接触AI编程的学习者来说，安装工具只是第一步。后续还需要逐步掌握需求描述、项目结构、代码验证、版本管理和智能体协作等能力。誉天教育也将持续整理AI编程工具、大模型应用开发和智能体工程相关内容，帮助学习者建立更加完整的实践路径。
