Codex CLI从安装到实战全流程

2026年8月15日
| 阅读

点击上方“全栈程序员社区”，星标公众号

重磅干货，第一时间送达

很多人第一次接触 Codex CLI，会把它理解成“终端里的聊天框”。真正用进项目后，它更像一位能读仓库、改文件、跑命令的工程搭档。

这篇从安装开始，把登录、仓库初始化、任务下达、变更审查和自动化执行走通。

🛠️ 先安装，再确认环境

macOS 或 Linux 可以使用官方独立安装方式：

<span leaf="">curl -fsSL https://chatgpt.com/codex/install.sh | sh</span>

安装完成后进入项目目录，启动 Codex：

<span><span leaf="">cd</span></span><span leaf="">&nbsp;your-project</span><span leaf=""><br></span><span leaf="">codex</span>

第一次运行时，按页面提示选择 ChatGPT 登录或其他可用方式。完成后可以执行：

<span leaf="">codex login status</span>

它会显示当前登录状态。如果遇到安装、配置或运行异常，codex doctor 能生成诊断报告，比盲目重装更有效。

🧩 先让 Codex 读懂项目规矩

进入交互界面后，不要马上让它“大改一遍”。先用 /init 生成 AGENTS.md，再补充仓库约定，例如测试命令、格式化方式、禁止修改的目录和提交要求。

接着让它完成一个只读任务：

解释这个项目的目录结构，指出启动入口、核心模块和测试方式，不要修改文件。

这一步能看出它是否找对项目边界。然后用 /status 查看配置，用 /permissions 调整操作范围。涉及生产脚本、数据迁移或大范围重构时，先收紧权限。

🚀 用一个小任务跑通实战闭环

第一次实战建议选择低风险、可验证的任务，例如“给用户列表接口补一个空值测试”。提示里写清目标、范围和验收标准：

只修改用户列表模块，为空数据响应补测试；先说明方案，再改代码；运行相关测试并汇报结果，不改公共依赖版本。

Codex 通常会先查看相关文件，再执行修改。要关注它有没有遵守范围、是否运行了正确检查、失败时有没有说明原因。

修改完成后可在交互界面使用 /review 检查变更，也可以在终端执行针对工作区的代码审查。审查重点包括边界条件、兼容性、异常路径和测试缺口。

🔁 会话中断也能继续

项目做到一半退出，不必重新解释全部背景。回到同一目录后可以续接最近会话：

<span leaf="">codex resume --last</span>

若要保留原会话并尝试另一条思路，可以用 fork 创建分支会话，避免不同方案搅在一起。

⚙️ 把重复任务交给非交互模式

当流程已经稳定，可以用 codex exec 运行一次性任务：

<span leaf="">codex&nbsp;</span><span><span leaf="">exec</span></span><span><span leaf="">"检查当前改动，运行相关测试，并输出简短结果"</span></span>

非交互模式适合脚本和 CI 场景，也支持结构化结果与续接会话。要限定工作目录、权限、命令范围和失败条件，敏感步骤保留人工确认。

📌 提高效率的三个习惯

第一，把任务拆成能验收的小块，不要只说“优化一下”；第二，把仓库规范写进 AGENTS.md，减少每次重复交代；第三，要求它运行测试并展示证据，不把“代码已经生成”当成“任务已经完成”。

程序员AI工具的价值，不是替你多敲几行，而是把“理解问题—修改代码—执行检查—审查结果”连成稳定闭环。先从一个真实小任务开始，跑通后再扩大范围，Codex CLI 才会从新鲜玩具变成可靠生产力。
